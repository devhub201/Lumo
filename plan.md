## Phase 8 Web Search

The registered `web_search` tool lives under `server/lumo/tools/web-search`. It uses provider-independent Zod input/output contracts, a replaceable `SearchProvider` interface, normalized source-attributed results, bounded limits, URL validation, freshness mapping, and safe empty-result behavior. The initial provider is `DuckDuckGoLiteProvider` because the managed API hub has no registered search provider in this project. It is isolated behind the provider interface so a future managed/paid provider can replace it without changing Core.

The Tool System registers `web_search` with the `network` permission and explicitly allowlists that permission. Tool Executor performs validation, permission enforcement, bounded Phase 7 retries, output validation, and normalized failure envelopes. `buildWebSearchContext` passes the resulting tool envelope through the existing Context Manager, where the current tool-result budget and source-preserving metadata apply. A backend-only `searchWeb` procedure exposes the capability for future orchestration/testing; the UI remains unchanged and automatic search routing is intentionally deferred.

## Phase 9 Calculator + Utility Tools

Phase 9 registers four deterministic, permission-free tools through the same Tool Registry: `calculator`, `unit_converter`, `statistics`, and `datetime_utility`. Calculator uses a bounded recursive-descent parser rather than `eval`; conversion uses explicit category tables; statistics validates bounded finite arrays; date/time operations require explicit timezone offsets for date strings and avoid a full calendar system. Each tool has typed Zod input/output schemas, enabled state, precise descriptions, and a deterministic handler.

The backend-only `runUtility` procedure invokes a selected utility through the existing Tool Executor and passes the normalized ToolResult through Context Manager budgets. No utility accesses network, files, shell, environment variables, or secrets, and no utility result is persisted as memory. Phase 7 normalized errors are retained for invalid expressions, division by zero, unsupported units, invalid numbers, overflow, and invalid dates. Phase 10 separately prepares validated utility plans; it does not execute them.

## Phase 10 Tool Selection / Routing Logic

Phase 10 adds `server/lumo/routing` with a deterministic `DeterministicToolRouter`. The router classifies requests as `direct_response`, `tool_call`, `clarification_required`, or `unsupported_request`; extracts arguments for the registered Web Search and Phase 9 utility tools; validates arguments through each existing tool schema; checks enabled state and declared permissions through the existing permission checker; and returns a bounded `ToolPlan` for the existing Tool Executor. It never executes tools directly and does not create a second registry or executor.

Routing uses only a bounded recent-message context and optional summary for safe anaphora such as “Convert that into miles.” It asks for clarification when expressions, units, values, dates, or search subjects are missing; avoids tools for explanations and basic conversation; blocks unsupported capabilities; and routes unexpected failures through the Phase 7 safe fault normalizer. `ToolPlan[]`, request depth, and call fingerprints provide a future multi-tool boundary, but Phase 10 emits at most one plan and does not implement autonomous chaining, recursion, or agent workflows. The backend-only `routeRequest` procedure and Core `routeRequest` boundary expose preparation for future orchestration without changing the UI or existing send execution path.
